NITKSAA Event Backend
Cloned Website Files Integration Review
Date: 2026-05-30
Scope: Static review only. No backend/app code was modified or rewired.

Executive summary
-----------------
The five cloned Website files are useful integration references, but they are not ready to be imported or wired directly into the current Alpha backend.

Current Alpha backend under backend/app is a working async FastAPI slice backed by events_db through asyncpg. It has validated event CRUD, registration, QR verification, check-in, and check-in attempt logging using X-Dev-User development auth.

The cloned backend/src files assume the Website backend layout, synchronous psycopg2 pools, website_db and alumni_db, Website table names such as website_users and website_audit_log, Firebase Admin credentials, internal JWTs, and notification tables that do not exist in the Alpha events_db schema.

Recommendation: keep asyncpg for the Event backend for now, adapt the cloned patterns into backend/app modules incrementally, and add production auth behind a compatibility layer that preserves current Alpha validation.

2. Purpose of each cloned file
------------------------------
backend/src/config/settings.py
- Website-style Pydantic settings module.
- Reads backend/.env through pydantic-settings.
- Defines DB_HOST, DB_PORT, DB_NAME, ALUMNI_DB_NAME, DB_USER, DB_PASSWORD, DB_SSLMODE, SECRET_KEY, ACCESS_TOKEN_EXPIRE_MINUTES, APP_ENV, ALLOWED_ORIGINS, APP_BASE_URL, GMAIL_APP_PASSWORD, NOTIFY_WEBHOOK_URL, and FIREBASE_PROJECT_ID.
- Builds psycopg2-compatible postgresql URLs for website_db and alumni_db.
- Has production Cloud SQL Unix socket handling hard-coded for the Website Cloud SQL instance.

backend/src/middleware/firebase.py
- Verifies Firebase ID tokens using firebase_admin.
- Mints an internal HS256 JWT using python-jose.
- Provides get_current_user dependency that validates the internal JWT locally.
- On each request, queries website_users for suspension and live Website role flags.
- Exposes require_user_type and require_alumni helpers.

backend/src/services/db.py
- Provides synchronous psycopg2 ThreadedConnectionPool instances.
- get_db() targets website_db.
- get_alumni_db() targets alumni_db.
- Yields RealDictCursor and commits/rolls back on context manager exit.

backend/src/services/alumni.py
- Provides fetch_alumni_info(firebase_uids).
- Uses get_alumni_db() to batch fetch alumni profile fields from alumni_db.alumni.
- Caches results with cachetools.TTLCache for 30 minutes.
- Returns alumni_id, fullname, graduationyear, and branch keyed by firebase_uid.

backend/src/services/notify.py
- Provides emit(event_type, actor_uid, recipient_uid, entity_type, entity_id, context).
- Writes audit rows to website_audit_log.
- Writes in-app notifications to notifications.
- Optionally sends Gmail SMTP email in a background thread.
- Checks notification_preferences and website_users.email.
- Contains many Website feature event templates, but no Event Alpha templates yet.

4. Import path conflicts
------------------------
The cloned files use Website import roots:
- from config.settings import settings
- from config.tenant_config import TenantConfig
- from services.db import get_db
- from services.db import get_alumni_db

The current Event backend uses:
- from app.config import get_settings
- from app.database import get_pool
- from app.middleware.dev_auth import get_current_user

Conflicts and breakages if wired directly:
- backend/src/middleware/firebase.py imports config.tenant_config, which does not exist in this Event repo.
- backend/src modules are not under the current app package, and backend/tests explicitly put backend/ on sys.path for imports like app.main. Imports like config.settings and services.db will not resolve unless sys.path/package layout changes are made.
- A top-level package named services would conflict conceptually with app.services.
- firebase.py defines get_current_user with the same role as app.middleware.dev_auth.get_current_user but with incompatible auth headers and behavior.
- settings.py defines a global settings object and env aliases that differ from app.config.get_settings().
- db.py defines get_db() as a synchronous cursor context manager, while current repositories/services expect asyncpg.Connection and awaitable calls.

Recommendation:
- Do not import backend/src directly from backend/app.
- Move/adapt selected code into app-owned modules when wiring starts, for example app/middleware/auth.py, app/services/alumni_service.py, app/services/notify_service.py, and app/config.py.
- Preserve the current app package root and avoid adding a second active source root.

6. Database connection differences
----------------------------------
Current backend/app:
- Uses asyncpg.
- Creates one async connection pool in app.database.get_pool().
- Services and repositories accept asyncpg.Connection.
- SQL placeholders use $1, $2, etc.
- Fits FastAPI async route handlers.

Cloned backend/src:
- Uses psycopg2 ThreadedConnectionPool.
- Provides blocking context managers yielding RealDictCursor.
- SQL placeholders use %s.
- Assumes website_db and alumni_db pools.
- Commits on every successful context manager exit.

Special focus: keep asyncpg or move to psycopg2?
- Recommendation: keep asyncpg.
- Reasons:
  - Current Alpha backend is already fully async and validated around asyncpg.
  - Existing repositories, services, health checks, tests, and SQL placeholder style all expect asyncpg.
  - Moving to psycopg2 would require a broad rewrite and risks breaking the validated Event API slice.
  - Blocking psycopg2 calls inside async route handlers can degrade concurrency unless carefully isolated.
  - The product requirement is to clone/review before continuing, not to standardize drivers immediately.

How to adapt:
- Keep app.database.get_pool() for events_db.
- Create async helpers for event_users, event_members, auth exchange, notifications, and audit using asyncpg.
- For alumni_db, either:
  - add a second asyncpg pool for alumni_db, or
  - introduce a narrow sync adapter only for alumni lookup, called through threadpool boundaries.
- Prefer a second asyncpg pool to keep operational behavior consistent.


7. Auth differences
-------------------
Current Alpha auth:
- Dependency-based dev auth in backend/app/middleware/dev_auth.py.
- Only active when APP_ENV=development.
- Uses X-Dev-User header.
- Built-in users:
  - admin: is_admin=True, permissions include event:create, event:update, event:checkin, event:export.
  - attendee: is_admin=False, permissions include event:register.
- Current routes depend directly on get_current_user or get_admin_user from dev_auth.
- Tests depend on X-Dev-User and APP_ENV=development.

Target cloned auth:
- Client sends Firebase ID token to an exchange endpoint.
- Backend verifies Firebase token using firebase_admin.
- Backend mints an internal HS256 JWT.
- Subsequent requests use Authorization: Bearer <internal JWT>.
- get_current_user decodes internal JWT locally.
- It performs a DB lookup on every request for suspension/live roles.
- Current clone checks website_users.status and Website role flags, not event_users/event_members.

Special focus: how to add POST /api/v1/auth/firebase safely
- Add a new router, e.g. app/api/auth.py, without changing existing event routes first.
- Endpoint shape:
  - POST /api/v1/auth/firebase
  - request: { "firebase_token": "..." }
  - response: { "token": "<internal JWT>", "user": {...} }
- In the endpoint:
  - Verify Firebase ID token once.
  - Extract firebase_uid, email, and display name.
  - Look up alumni_db by firebase_uid and/or email according to agreed identity rules.
  - Upsert event_users in events_db.
  - Do not overwrite existing user_type/ref_id with weaker/null values.
  - Mint JWT with stable claims: firebase_uid, user_type, ref_id, graduation_year, exp.
- Add tests that call route dependency overrides or mock token verification; do not require live Google calls in CI.
- Keep X-Dev-User dependencies in place until Bearer auth has separate test coverage.

Auth compatibility recommendation:
- Introduce a new auth dependency facade, for example app/middleware/auth.py:
  - In development, optionally accept X-Dev-User for existing tests.
  - Accept Bearer JWT for new production-style flows.
  - Export get_current_user, get_admin_user, and role helpers from one place.
- Migrate routes to the facade only after tests prove X-Dev-User behavior remains unchanged.


8. Notification/audit differences
---------------------------------
Current Alpha:
- No general notification service.
- No event_audit_log, notifications, or notification_preferences tables in the active migration.
- Check-in scan attempts are audited in check_in_attempts.
- Admin/event changes are not written to a general audit table.
- No email or push delivery.

Cloned notify.py:
- Writes audit rows to website_audit_log.
- Writes in-app notification rows to notifications.
- Reads notification_preferences.
- Reads website_users.email.
- Sends Gmail SMTP mail in background threads when configured.
- Contains Website event types, not Event Alpha event types.

Required adaptations:
- Rename audit target from website_audit_log to event_audit_log or another Event-owned audit table.
- Decide whether existing check_in_attempts remains separate from general audit. Recommendation: keep it for scan telemetry, and add event_audit_log for business/audit events.
- Ensure notifications table schema includes title and message if using cloned notify.py as-is. The integration note's sample notifications table omits title and message, while cloned notify.py inserts both.
- Replace website_users email lookup with event_users email lookup.
- Add Event templates, at minimum:
  - registration_confirmed
  - registration_cancelled
  - checkin_completed
  - event_published
  - event_cancelled
  - volunteer_assigned
- Make emit non-raising. It must not turn a successful registration/check-in into a user-visible 500 because email or notification write failed.
- If backend remains asyncpg, implement async DB writes or schedule notification side effects carefully after primary transaction success.


9. Alumni lookup differences
----------------------------
Current Alpha:
- Stores ref_id and firebase_uid on registrations and attendees as plain text.
- Does not query alumni_db.
- Registration body can provide ref_id; otherwise it falls back to user.ref_id from X-Dev-User.
- Duplicate prevention is by event+email and event+ref_id at service level.

Cloned alumni.py:
- Looks up alumni profile fields from alumni_db.alumni by firebase_uid.
- Uses directory_visible = true.
- Returns alumni_id, fullname, graduationyear, branch.
- Does not use ref_id as input despite the integration note saying fetch_alumni_info should be by ref_id in prose.

Gap:
- The active Alpha schema and service use ref_id heavily.
- The cloned alumni.py API is keyed by firebase_uid.
- Product guidance says ref_id points to alumni_db.alumni.alumni_id and should be treated as a read-only pointer.

Recommendation:
- Clarify and standardize lookup API before wiring.
- Prefer two explicit functions:
  - fetch_alumni_info_by_firebase_uids(firebase_uids: list[str])
  - fetch_alumni_info_by_ref_ids(ref_ids: list[str])
- Use alumni_db as source of truth for fullname, branch, and graduation year in read responses where needed.
- Do not store alumni profile fields in registrations/event_users except narrowly needed snapshots such as badge_name/email supplied for the event.

13. Risk areas
--------------
High risk:
- Breaking validated Alpha routes by swapping asyncpg for psycopg2.
- Import path collisions between backend/src and backend/app.
- Import-time settings failure because SECRET_KEY or DB_PASSWORD is missing.
- Auth route changes that invalidate existing tests and curl flows.
- Blocking DB calls in async handlers.
- Writing to non-existent Website tables.
- Mismatched notifications table schema: cloned notify.py inserts title/message but sample Event migration does not include them.
- Inconsistent alumni identity lookup by firebase_uid vs ref_id.

Medium risk:
- JWT secret naming and rotation differences between Website and Event app.
- Firebase project/source-of-truth drift between Flutter app config and backend FIREBASE_PROJECT_ID.
- Duplicate prevention changing from email/ref_id to firebase_uid too abruptly.
- Event coordinator/volunteer authorization becoming global instead of event-scoped.
- Email thread side effects during tests if Gmail config is accidentally present.

Lower risk:
- Adding dormant dependencies before code uses them.
- Keeping backend/src as untracked reference files if not imported.


14. Recommended phased migration plan
-------------------------------------
Phase 0: Freeze current Alpha behavior
- Keep backend/app logic unchanged.
- Run and preserve current backend validation.
- Treat backend/src as reference only.

Phase 1: Schema foundation
- Add event_users and event_members in a new migration.
- Add event_audit_log, notifications, and notification_preferences in a separate migration.
- Keep existing tables and columns intact.
- Add new constraints carefully, avoiding immediate changes that reject current Alpha test data.

Phase 2: Auth exchange without route migration
- Add app/api/auth.py with POST /api/v1/auth/firebase.
- Mock Firebase verification in tests.
- Upsert event_users.
- Mint internal JWT with agreed claims.
- Do not change existing event/admin route dependencies yet.

Phase 3: Auth dependency facade
- Create a single app-owned auth dependency module.
- In APP_ENV=development, keep X-Dev-User support.
- Add Bearer JWT support.
- Update a small route group or tests first.
- Verify all existing Alpha tests still pass.

Phase 4: Event membership authorization
- Populate event_members when:
  - a coordinator creates an event,
  - an attendee registers,
  - a volunteer is assigned.
- Add event-scoped role checks for coordinator/volunteer actions.
- Avoid global is_volunteer/is_admin expansion unless product explicitly requires platform admin behavior.

Phase 5: Alumni lookup
- Add alumni DB async pool or isolated adapter.
- Implement explicit lookup by firebase_uid and/or ref_id.
- Enrich read responses where needed without storing stale alumni profile fields.
- Keep registration write path resilient if alumni lookup is temporarily unavailable, based on product policy.

Phase 6: Notification/audit
- Adapt emit() to event_audit_log and event_users.
- Add Event templates.
- Start with audit-only calls in critical write paths.
- Then enable in-app notifications.
- Enable Gmail/email last and only with explicit config.

Phase 7: Cleanup
- Remove or archive backend/src reference files only after adapted app modules are in place and tests pass.
- Update backend README and .env.example.
- Add migration/runbook docs for production deployment.

Special focus answers
---------------------
Do we keep asyncpg or move to psycopg2?
- Keep asyncpg. The current Alpha backend is async, validated, and consistently built around asyncpg. Move Website patterns, not the Website DB driver, unless there is a later platform-wide decision to standardize on psycopg2.

How to add POST /api/v1/auth/firebase safely?
- Add it as a new route first.
- Mock Firebase verification in tests.
- Upsert event_users without touching current event routes.
- Mint the internal JWT with shared claim names.
- Keep current X-Dev-User flow in development until all existing validation passes with the new auth facade.

How to create event_users and event_members without breaking current Alpha flow?
- Add them in additive migrations.
- Do not add required foreign keys from existing registrations/attendees immediately.
- Backfill event_users from distinct current firebase_uid values where possible.
- Populate event_members for new registrations after the migration.
- Keep existing registrations.ref_id/firebase_uid nullable until production auth is mandatory.
- Add stricter NOT NULL/foreign key constraints only in a later migration after data is clean.

How to preserve existing validated event APIs?
- Do not rename existing endpoints or response fields.
- Do not change backend/app repositories/services in the auth exchange phase.
- Keep X-Dev-User tests passing.
- Add new behavior behind new modules and facade dependencies.
- Run the existing event flow tests after every phase.

How to keep current backend validation passing during migration?
- Additive migrations only.
- Keep APP_ENV=development behavior.
- Keep EVENTS_DB_URL.
- Do not import backend/src settings at app startup.
- Do not require SECRET_KEY, DB_PASSWORD, Firebase credentials, or alumni_db for current test collection.
