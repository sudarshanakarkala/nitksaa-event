2. PURPOSE OF EACH CLONED FILE
────────────────────────────────────────────────────────────────────────────────

backend/src/config/settings.py
  Purpose: Pydantic-settings config for the Website backend.
  Manages dual-DB connections (website_db + alumni_db), JWT signing key,
  Firebase project ID, CORS allowed origins, email/SMTP config, and Cloud SQL
  socket path resolution for production (Google Cloud Run). Exposes db_url,
  alumni_db_url, and origins_list as computed properties.

backend/src/middleware/firebase.py
  Purpose: Two-step authentication for the Website platform.
  Step 1 — firebase exchange: verify_firebase_token() validates a Firebase ID
  token against a specific Firebase project and returns decoded claims.
  Step 2 — JWT issuance: make_jwt() signs an internal 8-hour HS256 JWT.
  Per-request: get_current_user() FastAPI dependency decodes the JWT on each
  request and performs a live DB role-flag read (suspension check, is_admin,
  is_content_editor, etc.) from website_users table.
  Also exposes: require_user_type() dependency factory, require_alumni() inline
  guard.

backend/src/services/db.py
  Purpose: Synchronous psycopg2 connection pool manager.
  Maintains two ThreadedConnectionPools (lazily initialised):
    get_db()        → website_db  (reads + writes, platform features)
    get_alumni_db() → alumni_db   (read-only by convention, alumni identity)
  Uses RealDictCursor so rows are returned as plain dicts.
  Context managers handle commit-on-success and rollback-on-error.

backend/src/services/alumni.py
  Purpose: Cached alumni identity lookup.
  fetch_alumni_info(firebase_uids) queries alumni_db for fullname,
  graduationyear, and branch for a list of firebase_uids. Results are stored
  in a TTLCache (TTL=30 min, maxsize=5000) to avoid hammering alumni_db on
  every request. Cross-DB merge happens in Python — no SQL joins across DBs.

backend/src/services/notify.py
  Purpose: Three-layer notification and audit plumbing.
  Layer 1 (_write_audit)  — always fires; inserts into website_audit_log.
  Layer 2 (_write_in_app) — fires when recipient_uid set; inserts into
                            notifications table.
  Layer 3 (_dispatch_push)— fires in background thread; sends Gmail SMTP
                            email if gmail_app_password configured and user
                            not muted (notification_preferences table).
  Contains 25+ Website-specific event type templates (connections, mentorship,
  stories, communities, jobs, giving projects, etc.).
  Public API: emit(event_type, actor_uid, recipient_uid, entity_type,
                   entity_id, context).

  Fix: Add backend/src to sys.path in conftest.py, or add __init__.py files

CONFLICT 3 — Deferred import inside get_current_user()
  File:    backend/src/middleware/firebase.py, line 93
  Import:  from services.db import get_db   (inside async function body)
  Risk:    Works if sys.path is correct, but the deferred import pattern hides
           the missing-module error until the first authenticated request hits.
           Should be top-level once path conflicts are resolved.

  backend/app/services/ and backend/src/services/ both exist under backend/.

  it would NOT find backend/src/services/db.py (which is what firebase.py
  expects). It would silently fail or import nothing.

6. DATABASE CONNECTION DIFFERENCES
────────────────────────────────────────────────────────────────────────────────

                    ALPHA (backend/app)          WEBSITE SRC (backend/src)
                    ─────────────────────────    ─────────────────────────────
Driver              asyncpg 0.29.0               psycopg2 (sync)
Async               Yes — all await              No — blocking sync
Pool type           asyncpg.Pool                 psycopg2.pool.ThreadedConnectionPool
Pool init           await asyncpg.create_pool()  pool.ThreadedConnectionPool(1, 10, ...)
Connection acquire  async with pool.acquire()    context manager (getconn/putconn)
Cursor/Row type     asyncpg.Record               dict (RealDictCursor)
SQL param style     $1, $2, $3 (positional)      %s (psycopg format)
Database(s)         events_db (1 database)        website_db + alumni_db (2 databases)
Tables in scope     events, sessions,             website_users, website_audit_log,
                    registrations, attendees,     notifications,
                    check_ins, check_in_attempts  notification_preferences,
                                                  alumni (in alumni_db)
Lifespan            app lifespan (get_pool /      Process-scoped globals
                    close_pool)                   (_website_pool, _alumni_pool)
Connection reuse    await pool.acquire()          getconn() from thread pool
Error handling      async context manager         try/except + rollback in context manager

KEY INCOMPATIBILITY:
The entire Alpha backend/app is async FastAPI. asyncpg is native async.
psycopg2 is synchronous blocking. Running psycopg2 operations directly in an
async FastAPI route handler will block the event loop and cause request
starvation under any meaningful concurrent load.

Mixing the two is possible only by wrapping sync psycopg2 calls in
asyncio.to_thread() or fastapi.BackgroundTasks, but this complicates the code.

RECOMMENDATION: Keep asyncpg for all events_db operations (current Alpha).
For auth (firebase.py) the DB interaction (event_users table) should be done
via asyncpg, not psycopg2. If alumni_db is needed, wrap get_alumni_db() calls
in asyncio.to_thread(). Notify audit writes can use BackgroundTasks.

DO NOT move the Alpha event/registration/check-in repositories to psycopg2.

CURRENT AUTH FLOW (Alpha):
  Client sends X-Dev-User: admin → dev_auth.get_current_user() returns
  hardcoded dict → route handler receives user dict.
  Only works in development. Hard-blocks production use.

TARGET AUTH FLOW (from Website src):
  Step 1: Client calls POST /api/v1/auth/firebase with {id_token: <firebase_token>}
  Step 2: firebase.verify_firebase_token() validates token against Firebase project
  Step 3: Server looks up or creates user in event_users table
  Step 4: firebase.make_jwt() issues signed internal JWT (HS256, 8-hour expiry)
  Step 5: Client stores JWT, sends Authorization: Bearer <jwt> on each request
  Step 6: firebase.get_current_user() (FastAPI dependency) decodes JWT,
          performs live event_users DB lookup for suspension + role flags.

TRANSITION CONCERN:
  The current test suite (test_event_flow.py) is entirely built on X-Dev-User
  headers. If dev_auth.py is removed, all 7 existing test scenarios will fail.
  The X-Dev-User mechanism must be kept in parallel with Firebase JWT during
  the migration, gated on APP_ENV=development.

9. ALUMNI LOOKUP DIFFERENCES
────────────────────────────────────────────────────────────────────────────────

CURRENT ALPHA:
  ref_id comes from the X-Dev-User auth dict (ALUMNI-DEV-001, ALUMNI-DEV-ADMIN).
  No actual alumni lookup is performed. Alumni name is taken from registration
  form input (full_name field). No year/branch enrichment.

WEBSITE SRC (alumni.py):
  fetch_alumni_info(firebase_uids) queries alumni_db directly.
  SELECT firebase_uid, alumni_id, fullname, graduationyear, branch
  FROM alumni WHERE firebase_uid = ANY(%s) AND directory_visible = true
  Returns per-uid dict with fullname, graduationyear, branch, alumni_id.
  Cached (TTLCache, 30-min TTL, maxsize=5000).

GAPS FOR EVENT APP:
  1. alumni_db is a separate PostgreSQL instance (or schema). It is part of
     the Website infrastructure. It is NOT available in a standalone Event app
     dev environment without also running the Website backend.
  2. alumni.py uses psycopg2 (sync). Must be wrapped in asyncio.to_thread().
  3. The directory_visible=true filter means alumni who have set their profile
     to hidden will not appear — acceptable for display, but their event
     registrations must still work without enriched data.
  4. Event app currently has no event_members table. alumni_id → firebase_uid
     mapping must be established when a user authenticates via Firebase.

RECOMMENDED APPROACH:
  Phase A: Create event_users table (firebase_uid, email, user_type, ref_id,
           fullname, status). Populate on first Firebase login.
  Phase B: Create event_members table (event_user_id → alumni_id, year, branch)
           populated from alumni_db lookup at login time (not per-request).
  Phase C: Use event_members for display enrichment (attendee lists, check-in
           summary). alumni.py can be adapted to query event_members locally
           rather than alumni_db directly, removing the alumni_db dependency
           from the event app runtime.

13. RISK AREAS
────────────────────────────────────────────────────────────────────────────────

RISK 1 — TenantConfig ImportError (SEVERITY: CRITICAL)
  If firebase.py is imported before config/tenant_config.py exists, the entire
  backend will fail to start with an ImportError.
  Impact: Total startup failure.
  Mitigation: Fix BEFORE any wiring attempt.

RISK 2 — psycopg2 blocking the async event loop (SEVERITY: HIGH)
  Any psycopg2 db.py call made directly inside an async route handler will
  block the FastAPI event loop for the duration of the DB round-trip.
  Under load: all concurrent requests stall waiting for the blocking call.
  Impact: Performance degradation, request timeouts, asyncpg pool starvation.
  Mitigation: Wrap all psycopg2 calls in asyncio.to_thread(). Or better:
  convert auth and alumni DB ops to asyncpg.

RISK 3 — DB param style mismatch (SEVERITY: HIGH)
  asyncpg uses $1, $2 positional params.
  psycopg2 uses %s format params.
  Copying SQL queries from db.py into asyncpg code (or vice versa) without
  changing param style will cause runtime errors on first DB hit.
  Impact: Silent 500 errors on affected endpoints.
  Mitigation: All queries adapted for asyncpg must use $1/$2/$3 style.

RISK 4 — Firebase Admin SDK credential setup (SEVERITY: HIGH)
  firebase-admin requires Google Application Default Credentials (ADC) or a
  service account JSON file. Neither is configured in the current environment.
  In development: requires either `gcloud auth application-default login`
  (for the correct GCP project) or a downloaded service account JSON file.
  In production (Cloud Run): requires the Cloud Run service account to have
  the Firebase Authentication Viewer IAM role.
  Impact: verify_firebase_token() will raise 401 on every request until
  credentials are configured.
  Mitigation: Document credential setup. Provide GOOGLE_APPLICATION_CREDENTIALS
  env var pointing to service account JSON for local dev.

RISK 5 — SECRET_KEY missing from .env (SEVERITY: HIGH)
  settings.py declares SECRET_KEY = Field(...) with no default.
  Pydantic-settings will raise a ValidationError on startup if SECRET_KEY is
  not set. This will crash the Event app before serving any request.
  Impact: Total startup failure if SECRET_KEY is absent.
  Mitigation: Generate and add SECRET_KEY before wiring.

RISK 6 — event_users table does not exist (SEVERITY: HIGH)
  firebase.py's get_current_user() queries website_users (must be adapted to
  event_users). If event_users does not exist, the live role-check query fails.
  The current implementation has a fail-open except clause — it swallows the
  exception and returns a bare user dict. This means:
  - User can authenticate (good)
  - But is_admin and other flags are all False (bad — admins lose admin access)
  Impact: Admin endpoints become inaccessible to real Firebase users.
  Mitigation: Create event_users migration BEFORE wiring firebase.py.

RISK 7 — alumni_db unavailable in dev (SEVERITY: MEDIUM)

  db_url property hardcodes the Website project's Cloud SQL socket path. This
  will fail in any production Cloud Run deployment of the Event app.

  any production deployment.

SPECIAL FOCUS ANSWERS
────────────────────────────────────────────────────────────────────────────────

Q: Do we keep asyncpg or move to psycopg2?
A: KEEP asyncpg. Do not migrate the event/registration/check-in data layer to
   psycopg2. The Alpha is async throughout and asyncpg performs better under
   the async FastAPI model. When we need psycopg2 functionality from the cloned
   files (notify.py, alumni.py), wrap those specific calls in asyncio.to_thread()
   rather than converting the entire app. For the new auth endpoint (event_users
   table), write it directly in asyncpg.

Q: How to add POST /api/v1/auth/firebase safely?
A: Create backend/app/api/auth.py as a NEW file. Do NOT modify any existing
   api files. Register the router in main.py alongside the existing routers.
   The endpoint:
     1. Accepts {id_token: str}
     2. Calls verify_firebase_token() from the adapted firebase.py
        (no TenantConfig; uses settings.firebase_project_id)
     3. Queries/upserts event_users via asyncpg (same pool used by event APIs)
     4. Issues JWT with make_jwt()
     5. Returns {access_token, token_type, expires_in}
   This adds a new route prefix that does not conflict with /api/v1/events or
   /api/v1/admin. Existing tests are untouched.

Q: How to create event_users and event_members without breaking Alpha flow?
A: New SQL migration files only — no changes to existing tables.
   event_users: brand new table, no FK references from existing tables.
   event_members: new table, FK to event_users only.
   The existing tables (events, registrations, attendees, check_ins,
   check_in_attempts) do NOT reference event_users or event_members.
   Migrations are additive. Rolling back = DROP TABLE (no data loss on existing).

Q: How to preserve existing validated event APIs?
A: The existing API files (events.py, admin_events.py) and all their underlying
   services and repositories are NOT touched during migration phases 0-2.
   The X-Dev-User auth dependency remains in dev_auth.py.
   JWT auth is introduced as an ALTERNATIVE dependency in a new jwt_auth.py
   module. Only in Phase 2 (or later) do we optionally update route handlers
   to prefer JWT, with fallback to X-Dev-User in development.
   The test suite will catch any regression immediately.

Q: How to keep current backend validation passing during migration?
A: The conftest.py require_db fixture skips all tests if DB is unreachable.
   The client fixture uses APP_ENV=development, which keeps X-Dev-User active.
   As long as:
     (a) dev_auth.py is not removed or gated out in development mode
     (b) No existing table schemas are altered
     (c) No existing route paths are changed
     (d) The asyncpg pool lifecycle in main.py is preserved
   all 7 existing test scenarios will continue to pass throughout the migration.
