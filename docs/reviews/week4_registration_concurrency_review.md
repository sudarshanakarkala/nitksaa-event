## Registration Transaction Flow

```
1. pool.acquire()                           → dedicated connection from asyncpg pool
2. conn.transaction()                       → BEGIN
3. SELECT events WHERE event_id = $1        → acquires row-level lock
   FOR UPDATE
4. Check: event published                   → within locked transaction
5. Check: registration window open          → within locked transaction
6. get_active_for_user()                    → check duplicate, within transaction
7. count_active()                           → capacity check, within transaction
8. repo.insert()                            → INSERT registration, within transaction
9. repo.set_registration_number()           → UPDATE, within transaction
10. COMMIT                                  → lock released, row visible
```

---

## Row Locking Analysis

### The Lock

`SELECT events WHERE event_id = $1 FOR UPDATE` acquires a **row-level exclusive lock** on the events row for that event.

- This is a PostgreSQL-level lock, not application-level.
- All concurrent registrations for the **same event** contend on this single events row.
- Only one transaction holds the lock at a time; others block at step 3 until the holder commits or rolls back.

### What This Guarantees

When two requests arrive concurrently for event E with capacity 1:

```
Request A:  FOR UPDATE (acquired)
Request B:  FOR UPDATE (blocks — waits for A)

Request A:  count_active() → 0
Request A:  INSERT registration
Request A:  COMMIT → lock released, count now 1

Request B:  FOR UPDATE (now acquired)
Request B:  count_active() → 1  ← sees A's committed row
Request B:  1 >= capacity(1) → 409 event_full
```

**Result:** Capacity is never exceeded. The sequence of lock → count → insert is fully serialized per event.

## Defense-in-Depth: Partial Unique Index

Migration 008 added:

```sql
CREATE UNIQUE INDEX uq_registrations_active_per_user
    ON registrations (event_id, firebase_uid)
    WHERE status = 'registered';
```

This is a **database-level constraint** that prevents duplicate registrations for the same user+event combination regardless of application logic. Even if the `get_active_for_user` check failed (e.g., due to a bug), the INSERT would fail with a unique constraint violation before any duplicate row could be committed.

## Connection Pool Behavior

asyncpg uses a connection pool (`asyncpg.create_pool`). Each `pool.acquire()` provides a **dedicated connection** for the duration of the `async with` block.

- PostgreSQL transactions are connection-scoped — `BEGIN`/`COMMIT` are per-connection.
- `FOR UPDATE` locks are session-scoped — they are held until the transaction ends.
- No risk of lock being shared across connections within the same request.

---

## count_active() Isolation

`count_active()` is called inside the `FOR UPDATE` transaction:

```python
capacity = event_row["capacity"]
if capacity is not None:
    if await repo.count_active(event_id) >= capacity:
        raise HTTPException(status_code=409, detail="event_full")
```

Because we hold the events row lock, no other transaction can complete an INSERT for this event between our `count_active()` call and our own INSERT. The count is accurate at the point of the check.

asyncpg uses `READ COMMITTED` isolation by default (PostgreSQL default). Within our transaction, `count_active()` sees all previously committed rows. Combined with the `FOR UPDATE` lock, the check-then-insert is atomic from a capacity perspective.

## Scenarios Reviewed

| Scenario | Outcome |
|---|---|
| Two concurrent requests, capacity 1 | One succeeds, one gets `409 event_full` |
| Same user submits twice simultaneously | One succeeds, one gets `409 already_registered` (or unique index violation) |
| Capacity NULL (unlimited) | No capacity check — lock still prevents duplicate registrations for same user |
| Zero capacity remaining at check time | `count_active() >= capacity` → `409 event_full` before INSERT |
| Email send fails after INSERT | Registration committed, email status set to `failed` — no rollback |

## Not a Race Condition: Registration Number Generation

```python
reg_number = f"NITKSAA-{datetime.now(timezone.utc).year}-{registration_id:06d}"
```

The registration number is derived from `registration_id`, which is a `SERIAL` (or `BIGSERIAL`) primary key generated by PostgreSQL at INSERT time. Serial values are unique per row. No collision is possible even under concurrent load.

## Conclusion

The capacity enforcement is correct. No code changes are needed.

**Summary of protections in place:**

1. `SELECT ... FOR UPDATE` serializes concurrent capacity checks and inserts per event at the PostgreSQL level.
2. `count_active()` is called inside the locked transaction — the count is accurate and not subject to TOCTOU race conditions.
3. A partial unique index on `(event_id, firebase_uid) WHERE status='registered'` provides a DB-level backstop against duplicate registrations.
4. Email failures after `COMMIT` do not affect registration integrity.

The only scenario that would require additional work is **cancelation + re-registration under load** (e.g., if a cancelled spot should free capacity). That flow is not yet implemented and is out of scope for Phase 2.
